# Разработка Noxy с Codex

## Что уже подготовлено
Репозиторий пока находится перед S01: игрового кода и выбранного движка нет.
AGENTS.md задаёт общий контракт; три skills находятся в .agents/skills.
Скрипты в tools/ и GitHub Actions проверяют сам процесс уже сейчас.
Браузерные сценарии игры появятся вместе с S01, когда будет что запускать.

## Один раз настроить среду
Открой именно Shwedsky/Noxy на ветке с этими изменениями.
Для постоянного использования сначала включи изменения в main через PR.

Локально на Windows используй WSL2 и Node 24 LTS (версия указана в .nvmrc).
Из корня репозитория выполни:
```bash
node tools/setup.mjs
```
До S01 команда не скачивает игровые зависимости и явно сообщает об этом.
После появления root package.json + package-lock.json она использует npm ci.
При изменении lockfile запускай setup снова; не обновляй зависимости автоматически
до latest перед каждой задачей. Это делает результаты сборки воспроизводимыми.

Если работаешь в облачном Codex с полями Setup script и Maintenance script:
- подключи репозиторий Noxy;
- выбери Node 24;
- в оба поля сейчас добавь: node tools/setup.mjs;
- после добавления Playwright в S01 используй в обоих полях:
  node tools/setup.mjs --browser-with-deps;
- проверь успешное выполнение setup; после смены Node или базового образа сбрось
  кеш среды, если интерфейс предоставляет такую команду.

Флаг --browser ставит Chromium из локально закреплённой версии Playwright.
--browser-with-deps дополнительно ставит системные зависимости на Linux;
если среда запрещает их установку, нужен образ с готовыми зависимостями.
Флаг до появления зависимостей намеренно возвращает ошибку.

Для S01 нужен доступ к npm registry и серверам загрузки браузера во время установки.
Если ограниченная сеть блокирует установку, добавь конкретный домен из ошибки в
настройки разрешённых адресов среды. Проверяй документацию библиотек онлайн.
Для engine spike не нужны Telegram bot token, PostgreSQL, платный API или ключ LLM.
Продакшен-бот и его настройки пока не менять.

В локальном Codex/IDE skills обнаруживаются из .agents/skills. Если они не появились,
начни новую сессию/перезапусти клиент. Для интерфейса без списка skills попроси
прочитать соответствующий SKILL.md по пути — процесс от этого не зависит.
Глобальный AGENTS.md, системный prompt или сторонний plugin добавлять не требуется.

## Рабочий цикл
1. Выбрать один spec или явно назвать пакет из 2–3 смежных specs.
2. Автор читает $game-spec, фиксирует AC и реализует срез до проверяемого состояния.
3. Прогонять минимальные относящиеся к изменению проверки; при ошибке исправлять
   причину и повторять затронутые проверки.
4. После стабилизации отдельный read-only reviewer использует $game-review.
   В среде с subagents автор запрашивает его сам; иначе нужна отдельная задача.
   Передать spec, base/head и доказательства. Не передавать вердикт автора.
5. Исправить существенные замечания; повторно проверить изменённые участки.
6. PR содержит короткий отчёт по AC. Слияние — отдельное разрешение владельца.
   Один spec не обязан означать один PR, но пакет не должен расти по ходу работы.

Для review без subagents в новой задаче:
```text
Прочитай .agents/skills/game-review/SKILL.md и проверь текущую ветку
относительно main по активному spec. Сначала подтверди base/head.
Не меняй код. Дай дефекты с воспроизведением, незакрытые AC и вердикт.
```

## Быстрые и полные проверки
foundation — документы процесса, skills и тесты запускающего инструмента.
prototype — foundation + относящиеся к прототипу typecheck/логика/build/smoke.
milestone — prototype + расширенные интеграционные и браузерные сценарии.
release — milestone + полный настроенный автоматический набор релизной проверки.

Команда: node tools/verify.mjs PROFILE.
Профили накапливаются: старший включает младшие. Пустой обязательный профиль,
отсутствующая команда, зависание или ненулевой exit не превращаются в успех.
Exit 0 — выполненные команды прошли; 1 — команда упала; 2 — gate не настроен.
JSON-отчёт и логи сохраняются в artifacts/verification/ (в git не коммитить).

Пока runtime-профили пусты, prototype/milestone/release дают UNVERIFIED.
Это подготовка инструментов, а не заявка о готовности игры.

В S01 добавить корневой npm workspace и lockfile, закрепить Playwright и настроить:
- prototype: проверку типов, meaningful logic tests, production build обоих
  кандидатов, короткий browser smoke обоих; scripts не должны просто печатать PASS;
- milestone: расширенный ввод, resize, повторные запуски и измерения;
- release: оставить не настроенным до появления осмысленного release scope.

Каждая запись tools/verification.json содержит уникальный id, массив command
(программа и аргументы без shell) и timeoutSeconds от 1 до 1800.
Например, command ["npm", "run", "typecheck"] допустима только после создания
реального script typecheck. Сам runner не может оценить качество его assertions.

Browser smoke должен запускать production preview и завершать сервер после теста.
Тест должен проверять видимое поведение, ошибки console/pageerror, реальный ввод,
чистое состояние после restart. Для canvas/WebGL отдельно проверять изображение:
прочитать только внутренние координаты недостаточно. Не закреплять хрупкие
полноэкранные pixel snapshots для каждого изменения 3D-сцены.
Не заявлять реальные мобильные FPS по headless software renderer.

## Автоматизация в GitHub
Workflow Noxy verification запускается на PR и push в main.
До игрового workspace он проверяет foundation; после его появления изменения
кода, tooling, skills и конфигурации запускают prototype. Только Markdown в
docs/specs и README могут остаться на foundation.
Milestone/release можно запустить через Actions → Noxy verification → Run workflow.
Выбрать ветку и профиль. CI сохраняет отчёты и браузерные артефакты на 14 дней.
Значимые скриншоты/видео до истечения срока перенести в постоянные материалы
проекта или приложить к PR и сослаться на них в docs/evidence/.

Actions выполняет команды, но не организует независимое LLM-ревью сам по себе.
Его вызывает workflow skill автора или отдельная задача пользователя.
Защита main не включается этими файлами: чтобы GitHub запрещал merge при красном
CI, владелец может добавить required status check verify в branch rule после
первого запуска workflow. Платный API для этого pipeline не используется.

## Milestones и границы демо
Сохраняем Gates A–F из ROADMAP. Большие проверки — после S01, S06, S11, S14,
S25 и перед релизом, плюс при изменениях с реальным платформенным риском.
Внутренний core prototype после S06 не равен первой публичной playable release.
Обязательства S00/GDD про М/Ж, две валюты и аккаунт в первом выпуске сохраняются.
Не переносить весь backend/экономику/кастомизацию в S01 ради этих обязательств.

S01 может дать предварительную рекомендацию по desktop-замерам при отсутствии
телефона. Реальный mobile/Telegram gate при этом остаётся UNVERIFIED.
Не объявлять финальный выбор доказанным или Gate A пройденным без его evidence.
Продолжить следующий этап с таким риском можно по явному решению владельца;
deferred check сохраняется открытым и не получает PASS.

## Goals — по желанию
Если текущий клиент поддерживает /goal, используй его для долгой задачи с
проверяемым концом. Коммит не включает Goal и не активирует его в новой сессии.
Документация указывает поддержку начиная с Codex CLI 0.128.0.
Если команды в твоём интерфейсе нет, используй обычный запрос ниже — не трать
время на обязательную миграцию клиента ради этой функции.

Стартовая задача:
```text
Используй $game-spec. Выполни specs/S01-engine-spike.md в отдельной ветке.
Сравни оба обязательных движка, настрой реальные проверки prototype/milestone,
получи измерения и browser evidence, затем запусти независимое $game-review.
Исправляй найденные ошибки до проверяемого результата. Не начинай S02.
Недоступные device/Telegram проверки оставь UNVERIFIED и дай точные шаги.
При реальном блокере закончи отчётом с попытками, evidence и способом разблокировки.
Создай PR; не сливай его и не публикуй игру.
```

Вместо просьбы «делай бесконечно» у Goal должны быть AC, способ проверки,
границы scope и остановка при недоступном инструменте/данных или лимите.
